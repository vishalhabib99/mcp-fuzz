# mcp-fuzz build log

The full narrative history of how `mcp-fuzz` was built, dogfooded and fixed: what each real-world run found and what changed because of it. It moved here from the [profile README](https://github.com/vishalhabib99) on 2026-09-23 so the profile stays short. The text is unchanged.

mcp-doctor's companion (`pip install mcp-runtime-check`): instead of reading source, it launches a real MCP server and calls its tools with inputs derived from their own JSON schema, checking whether it fails cleanly or crashes/hangs. 24 real-world passes so far, up to 61K★ — real crash and mislabeling bugs filed on `mcp-server-chart` (confirmed fixed on a live rescan), `shadcn-ui-mcp-server`, and `codebase-memory-mcp` (42.7K★, official-scale). An external maintainer ([`agent-inspect`](https://github.com/rajudandigam/agent-inspect)) shipped a feature in their own tool in direct response to a finding this surfaced. Also checks latency, response size, concurrency, resource lifecycles, token-cost estimation with an opt-in dollar figure, and (via `--url`) a remote server over Streamable HTTP, not just a local stdio launch.

24 real-world passes so far, up to 61K★ (`upstash/context7`) — including Ant Design's official `mcp-server-chart` (4.3K★) — all 27 tools crashed instead of erroring cleanly on realistic bad input, [filed upstream](https://github.com/antvis/mcp-server-chart/issues/323) and confirmed fixed on `main` after a live rescan — a real crash bug [filed on `shadcn-ui-mcp-server`](https://github.com/Jpisnice/shadcn-ui-mcp-server/issues/61) (3K★), and a tool-annotation mislabeling [filed on `codebase-memory-mcp`](https://github.com/DeusData/codebase-memory-mcp/issues/2118) (42.7K★, official-scale). An external maintainer ([`agent-inspect`](https://github.com/rajudandigam/agent-inspect), a trajectory-debugging tool for TypeScript agents) asked to feed a real mcp-fuzz session into their evidence model — shipped `--full-trace` (v0.1.5) for full-fidelity JSONL export in response. The finding it surfaced (a healthy, 100%/A crash-resilience session reads as almost entirely failed once isError:true rejections collapse into a generic error status) was substantial enough that the maintainer asked for a reproducible write-up — filed as [agent-inspect#362](https://github.com/rajudandigam/agent-inspect/issues/362), with a verified fix demonstration built against AgentInspect's own outcome_observed schema. AgentInspect shipped a fix in response (v6.26.0, `--preset behavioral-session`) that scores outcome-level failures without collapsing a healthy session into a failed run, verified against the same sanitized gist and merged into their own repo's recipe fixtures. Also hardened the schema generator against adversarial `tools/list` metadata — found and fixed three real self-bugs (non-dict schema fields, a 5000-level-deep schema blowing the recursion limit). Also ran end-to-end against `oraios/serena` (29K★) with a real Python language server actually active (not a stub) — 28/28 tools tested with `--include-destructive`, 0 crashes, 100%/A, the deepest real-server coverage of any repo audited so far. Also added a real, scored **latency check** — the fourth axis (correctness/safety/groundedness/latency) alongside the other two tools — flagging a tool's valid call as slow via an absolute threshold or as a >3x outlier against its own server's median; re-running against `oraios/serena` found two real relative outliers (`create_text_file` at 9.4x median, `get_current_config` at 4.6x), 92.9%/B. Most recently, added a matching **response-size check** — same design, applied to payload size instead of response time, catching a tool that burns an agent's context window for no reason its description would predict; re-running against `oraios/serena` found four real relative outliers (`onboarding` at 17.2x median, `get_current_config` at 13.4x, plus two smaller ones), 85.7%/C. Most recently, added an opt-in **concurrency check** (`--concurrency N`): launches N independent connections (each its own subprocess) and calls a tool with identical arguments on all of them at once — a real test of concurrent access to a shared backend (a file, database, lock), not synthetic fan-out over one connection. Verified two ways: a new fixture tool with a genuine, reproducible race (a naive create-exclusive lock file) gets caught reliably; the official `modelcontextprotocol/server-memory` reference server comes back clean — an honest result, since each of its subprocesses keeps its own independent state, nothing to race on. Same full-checklist pass on `sooperset/mcp-atlassian` (5.9K★): 58/98 tools tested, 100%/A across crash resilience, latency, response size, and concurrency — the largest real target run against the complete toolkit, genuinely clean. Most recently, added an opt-in **resource-lifecycle check** (`--sequential`): every check above tests one tool call in isolation with synthetic arguments — this one detects `create_X`/`get_X`/`delete_X`-shaped tool groups by name, chains the *real* id a create call actually returns into the read/delete calls, then re-reads that id after deletion to catch a stale read (a resource that still reads as present after being deleted). Verified against a deliberately-planted bug in the test fixture (a fake delete that reports success but never removes the record) — caught correctly, with a clean healthy trio alongside it producing no false positive. Shipped as v0.5.0. Most recently, extended `--sequential` to a different bug class: **cross-resource (parent/child) lifecycle checking** — detects when one resource's create call takes another resource's real id as a parameter, then runs create-parent → create-child → delete-parent → read-child, flagging a still-readable child as a neutral orphaned-reference observation rather than a scored pass/fail (cascade-delete and orphan-allowed are both legitimate designs). Verified against two planted fixture cases: a non-cascading pair (caught) and a correctly-cascading pair (correctly not flagged). Shipped as v0.6.0. Most recently, turned the latency/response-size checks into a live runtime gate (`LatencyGate`, v0.7.0) — same absolute-threshold-plus-outlier design, applied to real calls an agent makes during a live session instead of one synthetic call per tool. One real design change, not a mechanical port: a batch audit only ever compares one tool's single call against unrelated *sibling* tools on the same server, but a live session calls the same tool repeatedly, so the gate tracks each tool's own call history and flags what's unusual for *that tool*, not its neighbors. Verified against a real crash and a real timeout (new fixture tools, not mocked) and dogfooded live against the official `@modelcontextprotocol/server-memory` reference server. Pairs with `mcp-reality-check`'s new correctness gate below — one call site, two independent live checks. Most recently, added a **token cost estimate**: rolls the response-size check's existing ~4-chars/token rule of thumb up into one whole-session total — what it would cost an agent's context window to call every tested tool once. Deliberately tokens only, never dollars — a real `$` figure depends on which model consumes the response and its current per-token pricing, neither of which this tool can know without guessing. Always computed, no new flag, since it's a pure rollup of data the response-size check already gathers. Released as `v0.8.0`. Most recently, added an opt-in **dollar-cost estimate** (`--price-model`) on top of the same rollup — restricted to a small, fixed list of currently supported Claude models with verified list *input* prices (a tool's response becomes input tokens for whichever model reads it next), never a default or a guess: an unrecognized model name is a clean CLI error listing the supported names. Verified against a real target: the official `@modelcontextprotocol/server-memory` reference server priced at `claude-haiku-4-5`, ~64 tokens across 3 tools, ~$0.0001. Released as `v0.9.0`. Most recently, added **Streamable HTTP support** (`--url`/`--header`) alongside stdio — previously hardcoded stdio-only, a gap confirmed blocking real dogfooding this session: one of the day's own breadth-check targets, `pipedrive-mcp-server`, supports both transports but could only be reached in stdio mode. Also fixed a real robustness bug this surfaced: the crash handler's reconnect always assumed relaunching would work — true almost always for a stdio subprocess this tool owns, but not for a remote server a tool call just killed, since this tool has no way to relaunch a process it doesn't own. A failed reconnect used to raise straight out of the run, crashing everything; now tracked via `terminated_early`, skipping the remaining tools instead — verified with a real subprocess crash over a real HTTP connection (the fixture's own `kills_process` tool), not just reasoned about. Verified against a real external target: [`WillDent/pipedrive-mcp-server`](https://github.com/WillDent/pipedrive-mcp-server), built from source and run over HTTP with a real `Authorization` header — 16/16 tools tested, 100%/A. Released as `v0.10.0`.

**v0.10.1 (2026-09-24): fixed false "slow" and "bloated" flags on fast servers.** A local run on 10 servers that need no API keys (the MCP reference servers, `chrome-devtools-mcp`, `desktop-commander`, `n8n-mcp`, `serena`) showed the relative outlier checks (3x this server's median) had no minimum. 8 of 10 latency flags were calls under 25ms, for example a 2.7ms `echo` on `server-everything` flagged against a 0.9ms median. A relative outlier now also has to exceed 100ms, or 1,000 chars for response size, in both the one-shot report and `LatencyGate`. After the fix the only flags left were real: `desktop-commander`'s `list_processes` returned ~26K est. tokens in one call, and `chrome-devtools-mcp`'s `get_console_message` took 475ms against a 2ms median. All 10 servers scored 100% on crash resilience. `mcp-server-chart` was left out of the runtime run because its tools send data to AntV's hosted renderer.
